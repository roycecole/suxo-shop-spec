## 1. 範圍

| 支援語言 | 狀態 |
|---|---|
| 繁體中文（`zh-Hant`） | **預設語言**，所有內容一定要有這個語系版本 |
| 英文（`en`） | 支援，可能有未翻譯內容（見 §4 Fallback 策略） |
| 日文（`ja`） | 支援，可能有未翻譯內容 |

**適用範圍**：電商平台的前台（[07-storefront-requirements.md](07-storefront-requirements.md)）與賣家後台（[08-vendor-admin-requirements.md](08-vendor-admin-requirements.md)）。**ShyeCMS 不在本輪範圍**——`shyecms-admin` 是拾夜科技內部台灣員工使用的工具，暫定維持繁體中文單一語系，若未來有需要另外提出（比照 [27-pwa-and-accessibility.md](27-pwa-and-accessibility.md) §4 排除 ShyeCMS 的慣例）。

## 2. URL 路由策略

採**路徑前綴**（Next.js i18n 路由），與既有 SSG/ISR 需求相容，且對 SEO 友善（各語言各自獨立可索引的網址，符合 [06-ecommerce-platform-architecture.md](06-ecommerce-platform-architecture.md) §5 的 SEO 訴求）：

```
/products/珍珠芭樂-5斤裝        → 預設語言（繁中），不加前綴
/en/products/珍珠芭樂-5斤裝     → 英文
/ja/products/珍珠芭樂-5斤裝     → 日文
```

賣家後台（Vite SPA，無 SEO 需求）改用簡單的語言切換器 + `localStorage` 記住選擇即可，不需要路由前綴。

## 3. 內容翻譯的資料模型策略

多語系內容（商品名稱/描述、分類名稱、CMS 頁面內容等）需要儲存多語系版本。採**獨立翻譯表**模式，而非在每張主表加 `_en`/`_ja` 欄位：

```
Translation
├── EntityType   （如 "Product"、"Category"、"PageSection"）
├── EntityId
├── LocaleCode   （"zh-Hant" / "en" / "ja"）
├── FieldName    （如 "Name"、"Description"）
└── Value
```

**為什麼選這個模式而非每張表加語言欄位**：未來若要新增第四種語言，不需要對每張表做 Migration，只是多寫幾筆 Translation 資料；缺點是查詢時需要多一次 join，但考量到目前規模（單一客戶部署，非高流量），這個代價可接受。

**受影響的服務**（凡是有面向使用者文字內容的服務，都需要查詢 Translation）：

| 服務 | 需要翻譯的欄位 |
|---|---|
| [12-service-catalog.md](12-service-catalog.md) | Product.Name/Description/ShortDescription、Category.Name、Tag.Name |
| [20-service-cms.md](20-service-cms.md) | PageSection.Config 內的文案（Banner 文案、RichText 內容，見 [28](28-i18n.md) 與 Markdown 決策的交互，本文件 §5 有說明） |
| [16-service-promotions.md](16-service-promotions.md) | 優惠券顯示文案（如有） |
| [21-service-shipping.md](21-service-shipping.md) | 物流方式顯示名稱 |

每個需要翻譯欄位的服務，各自的資料庫內建立 `Translation` 表（掛在自己的 schema 下，不是集中式的共用服務），沿用既有「服務各自擁有資料」的原則（[06-ecommerce-platform-architecture.md](06-ecommerce-platform-architecture.md) §4）。

### 3.1 共用套件 `SuxoShop.Shared.Translation` 的內容

[26-project-structure.md](26-project-structure.md) §3.1 已規劃這個共用 NuGet 套件（`ecommerce-services/shared/SuxoShop.Shared.Translation/`），但先前沒有文件說明它實際提供什麼。**它不是集中式的翻譯服務**——每個服務仍各自擁有自己 schema 下的 `Translation` 表（見上文），這個套件只負責讓 4 個服務（[12](12-service-catalog.md)、[16](16-service-promotions.md)、[20](20-service-cms.md)、[21](21-service-shipping.md)）不必各自重新實作同一套查詢/邏輯：

| 內容 | 說明 |
|---|---|
| `TranslationEntry`（共用 EF Core 實體設定） | `EntityType`/`EntityId`/`LocaleCode`/`FieldName`/`Value` 的欄位定義與索引設定（`(EntityType, EntityId, LocaleCode, FieldName)` 唯一索引），供各服務的 `DbContext` 用 `ApplyConfiguration` 套用，確保 4 個服務的 `Translation` 表結構完全一致，不會有人漏加索引或欄位型別不一致 |
| `ITranslationLookup.GetValueAsync(entityType, entityId, fieldName, locale)` | 查詢單一欄位的翻譯值，內建 §4 的 Fallback 邏輯（查無該語言版本時自動退回 `zh-Hant`），呼叫方不需要自己重複實作 fallback 判斷 |
| `ITranslationLookup.GetValuesAsync(entityType, entityIds, fieldName, locale)` | 批次查詢版本，避免清單頁（如商品清單）逐筆查詢造成 N+1 |

各服務仍需自己撰寫寫入邏輯（`PUT`/`POST` 端點如何更新 `Translation` 表），套件只統一「表結構」與「讀取＋fallback」這兩件事，避免 4 個服務各自寫出行為微妙不同的 fallback 判斷。

## 4. Fallback 策略

以「主要以中文為主」為前提：**任何欄位若該語言沒有翻譯，一律 fallback 到繁體中文**，不顯示空白或原始欄位鍵名。這代表繁體中文（`zh-Hant`）版本是唯一**強制要求**填寫完整的版本，英文/日文允許部分缺漏。

## 5. UI 文字（非使用者輸入內容）

前台/後台介面本身的固定文字（按鈕、標籤、錯誤訊息）採標準 i18n 函式庫的語系檔（JSON），不透過 Translation 表（那是給使用者輸入的動態內容用的）：

| 專案 | 函式庫 |
|---|---|
| 前台（Next.js） | `next-intl` 或 `next-i18next` |
| 後台（Vite SPA） | `react-i18next` |

## 6. 與既有決策的交互影響

- **WooCommerce 匯出**（[08-vendor-admin-requirements.md](08-vendor-admin-requirements.md) §5）：CSV 匯出**只匯出繁體中文（預設語言）版本**，WooCommerce 標準 CSV 格式沒有原生多語系欄位（那需要額外的多語系外掛如 WPML），本輪不處理多語系匯出。
- **Markdown 內容編輯**（見 [08](08-vendor-admin-requirements.md)、[12](12-service-catalog.md)、[20](20-service-cms.md) 的 Markdown 決策）：每個語言版本的 Markdown 內容各自獨立輸入，不是同一份內容機器翻譯，翻譯品質與提供方式見 §8。
- **PWA 快取**（[27-pwa-and-accessibility.md](27-pwa-and-accessibility.md)）：Service Worker 快取 key 需要包含語言前綴，避免不同語言版本的頁面互相快取覆蓋。

## 7. 明確排除：本文件不涵蓋幣別/日期/數字在地化

「多語系」直覺上常常包含幣別、日期、數字格式一起在地化，但本文件**只處理文字翻譯**，以下**明確不在範圍內**，避免日後誤以為已經涵蓋：

| 項目 | 現況 |
|---|---|
| 幣別 | 全平台維持**新台幣（TWD）單一計價**，即使切換到英文/日文介面，價格仍顯示 NT$，不換算成 USD/JPY。若英文/日文版面向的是海外客群（而非在台外籍人士/觀光客），這個假設需要重新確認 |
| 金流商付款頁語言 | 綠界/藍新等台灣金流商的付款頁面**本身是繁中介面**（見 [18-service-payment.md](18-service-payment.md)），與商店前台的語言選擇無關——買家用英文/日文瀏覽到結帳最後一步，會跳轉到一個繁中的金流付款頁，體驗不連貫，目前無法改善（金流商未提供多語系頁面的選項不在本平台控制範圍內） |
| 日期/數字格式 | 沿用系統預設格式（如 `2026-09-08`），不依語言別切換成 `Sep 8, 2026` 或 `2026年9月8日` 等在地化格式 |

**建議**：若日後確認英文/日文版真的要服務海外客群（而非僅台灣境內的外語使用者），需要另外規劃幣別轉換（含匯率來源、鎖價時機）與金流商的多語系或替代方案（如串接國際卡務或跨境金流），這是與現有金流架構（[18-service-payment.md](18-service-payment.md)）有直接衝突、需要重新設計的項目，不是本文件能夠涵蓋的擴充。

## 8. 待決議事項

- [ ] 日文/英文版本的 SEO 優先度是否與繁中版本相同（影響 [06](06-ecommerce-platform-architecture.md) §5 SSG 預產清單是否要依語言分別計算）
- [ ] Notification Service（[23-service-notification.md](23-service-notification.md)）LINE 通知訊息是否需要多語系，目前假設 LINE 官方帳號僅服務台灣市場，維持繁中單一語系
- [ ] 賣家後台是否要求賣家至少填寫繁中版本才能上架（資料完整性檢核）
